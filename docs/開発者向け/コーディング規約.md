# コーディング規約

## 背景・目的・適用範囲

このプロジェクトでは、Python版とGDScript版を並行して保守します。読み手がコードや説明の意味を推測しなければならない書き方は、バグ、仕様の誤解、移植時の差異を生む原因になります。

本規約の目的は、人間が読みやすく、安全で、効率がよく、変更しやすい実装と文書を維持することです。以下のR01〜R20は必須の禁止基準です。「動くから」「CIが通るから」という理由で違反を許可しません。

製品コード、テスト、開発ツール、起動スクリプト、CI設定、仕様書、設計書、README、操作説明へ適用します。既存コードが全基準へ適合済みであることは、この文書の追加だけでは保証しません。既存の違反を発見した場合は記録し、変更箇所で新たに作らないでください。安全性や正しさに関係する違反は修正するまで承認しません。

## 禁止基準

| ID | 禁止する実装・説明 |
| --- | --- |
| R01 | 処理の流れを文章として説明できない書き方、読解のために複雑な式や暗黙の副作用を解きほぐす必要がある書き方を禁止します。 |
| R02 | 何をするか、何を表すか、何を所有するかが直感的に分からない関数名・クラス名・変数名を禁止します。 |
| R03 | 状態や関数を主体的に所有するまとまりがあるのに、その所有者をクラスとして表現せず散在させる実装を禁止します。 |
| R04 | JSON-like Comment Outsの規則に準拠しない宣言コメント、宣言コメントの欠落、実装と食い違うコメントを禁止します。 |
| R05 | 不正入力、境界値、状態遷移、重複実行、例外、共有状態などを考慮せず、バグを生む可能性を残したコードを禁止します。 |
| R06 | 想定するデータ量に対して不必要な全走査、繰り返し計算、不適切な探索やデータ構造を使う、アルゴリズム的に効率の悪いコードを禁止します。 |
| R07 | 長すぎて責務や処理の位置を追えず、分割すべき内容を詰め込んだファイルを禁止します。 |
| R08 | ひとつのクラスが独立した複数の責務を所有する実装を禁止します。 |
| R09 | ひとつの関数が独立した複数の処理単位を実装する書き方を禁止します。 |
| R10 | 意味のある処理のまとまりごとに、目的や理由を説明するコメントが付いていないコードを禁止します。 |
| R11 | 不要な重複、同じ意味の別実装、不要な条件・変換・間接呼び出しなど、冗長なコードを禁止します。 |
| R12 | 根拠なく実行パフォーマンスへ悪影響を与える、頻繁なI/O・過剰な割り当て・コピー・変換・再構築などを禁止します。 |
| R13 | 対象や権限を確認しない削除・上書き・移動、機密情報の露出、実セーブを使うテストなど、危険な操作を禁止します。 |
| R14 | 変更箇所が不要に広がる密結合、仕様値の散在、既存のデータ契約を破るハードコードなど、拡張性のないコードを禁止します。 |
| R15 | 構文、lint、型検査、ビルド、単体・統合テスト、責務境界など、対象プロジェクトで必要な一般的なCI検証に失敗するコードを禁止します。 |
| R16 | 利用者の実行手順、画面遷移、保存・読込・再起動を含む必要なE2Eテストに失敗するコードを禁止します。 |
| R17 | 人間が前提、入出力、状態、制約、操作を把握できない仕様書・設計書を禁止します。 |
| R18 | 利用者への指示を「してください」、アプリの動作を「します」「なります」で書き分けず、主語と述語が対応しない説明を禁止します。 |
| R19 | 機能や手順の説明に、背景・目的・手段・ユーザーの実行方法が書かれていない文書を禁止します。 |
| R20 | 主語、目的語、条件、参照先が曖昧な文、誤った助詞、過剰な名詞の連結や直訳など、日本語として読みにくい説明を禁止します。 |

## コードの読みやすさと命名（R01・R02）

制御の流れを上から順に読める形にしてください。複雑な条件、深いネスト、入れ子の三項演算子、副作用を含む式は分けてください。短くするために意味を隠さないでください。

関数名は動作と対象、クラス名は担当する領域と責務、変数名は対象と状態が分かる名前にしてください。たとえばload_party_preset、BasicDefendAction、active_party_idsのように、読み手が役割を説明できる名前にしてください。

process、do、manager、data、tmpなど、単独では対象や役割を特定できない名前を公開契約へ使わないでください。短いローカル名も、範囲内で意味が明確な場合だけ使ってください。時間、座標、個数などは、必要に応じて単位と種類を名前へ含めてください。コメントを読まなければ名前の意味が分からない場合は、まず名前を直してください。

## 所有者・責務・分割（R03・R07〜R09・R14）

状態、設定、依存先、または関連する操作を主体的に所有するまとまりは、責務の分かるクラスとして表現してください。どこが状態の正本で、誰が変更できるかを明記してください。関連状態と処理をグローバル変数や複数モジュールへ散在させないでください。状態のない独立した純粋計算まで、形式だけのクラスで包むことは求めません。

クラスはひとつの責務を持ち、関数はひとつの目的に対するひとつの処理単位を実装してください。入力、計算、保存、描画の独立した処理を同じ関数へ詰め込まないでください。呼出順を調停する関数は処理の呼び出しだけを担当し、呼び出す先の実処理を自身へ取り込まないでください。

ファイルの責務を一文で説明できず、独立した領域や変更理由が複数ある場合は分割してください。長さの確認では、コードの量だけでなく、読む範囲、ネスト、分岐、所有する宣言の数も確認してください。コメントを削って見かけの行数を減らすこと、責務境界を壊して小ファイルへばらすことは禁止します。未分割の長大なファイルを便利な追加先として使い続けないでください。

既存のUI / Process / Dataと、調停処理と実処理の境界を守ってください。詳細は[責務分離の規約](CODING_RULES.md)を参照してください。必要な拡張点を既存の契約、データ定義、依存注入へ置き、想定のない将来のために不要な抽象化を増やさないでください。

## 宣言コメントと処理ごとのコメント（R04・R10）

[JSON-like Comment Outsの日本語正本](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md)に準拠してください。導入時の詳細と検査範囲は[宣言コメントの規約](COMMENT_RULES.md)を参照してください。

クラスには責務と主要フィールド、関数・メソッドには責務、実際の順序に沿った処理、引数、戻り値を記述してください。宣言名と実際の引数名を合わせ、入力がない場合や戻り値がない場合も明記してください。公開・非公開・ネストした宣言、テスト、ツールを除外しないでください。

本プロジェクトでは、実装内部の意味のある処理のまとまりごとにも、通常コメントを必須にします。宣言前の処理一覧だけで済ませず、実装内部の区切り、目的、理由、注意点を説明してください。内部コメントをJSON風にする必要はありません。宣言の概要と内部コメントは、意味と順序がおおむね対応するようにしてください。

単に「値を代入する」「ループする」とコードを言い換えるコメントや、名前を日本語へ置き換えただけの説明では不十分です。実装や仕様を変更したらコメントも更新してください。静的検査の成功は、説明の内容、読みやすさ、内部の全処理コメントを保証しません。人間による確認も行ってください。

## 正しさ・効率・安全（R05・R06・R11〜R14）

正常系だけでなく、不正型、未知キー、境界値、非有限値、欠損、重複、再実行、途中失敗、コピーと共有状態、状態遷移を確認してください。必要なケースは再現可能な回帰テストへ残してください。例外を握りつぶすことや、失敗を成功として返すことは禁止します。

想定する件数と呼び出し頻度を示し、探索や更新の計算量を説明できる方式を選んでください。重複した読み取りや計算は、必要な範囲で共用してください。キャッシュを導入する場合は、寿命、更新時点、破棄条件を明確にしてください。

頻繁に通る処理を変更する場合は、代表的なデータ量で変更前後を計測してください。計測条件と結果を記録してください。静的な計算量、実行時間、メモリ、I/Oを区別し、数値だけを良く見せるために検査条件を緩めないでください。

破壊的操作の前に、対象の絶対パス、操作の必要性、権限、復元方法を確認してください。曖昧な対象のまま操作しないでください。既存のユーザー変更と実セーブを保持し、テストには専用の一時領域を使ってください。秘密情報をログやコミットへ含めないでください。依頼されていないpush、公開投稿、PR変更などの外部操作は行わないでください。

## CI・E2Eとレビューの判定（R15・R16）

変更に必要な構文・lint・型・ビルド・単体・統合・責務境界の検証を実行してください。対象プロジェクトが採用する検査を根拠なく省略しないでください。

利用者に見える変更では、操作、画面遷移、保存、読込、再起動を含む必要なE2Eシナリオを確認してください。単体・統合・headless・smokeの成功を、実GUI、E2E、配布exportの成功と言い換えないでください。E2Eカタログの構造検査は、E2E実行の代わりにはなりません。

検証に失敗した場合は、原因と影響を修正するまで承認しません。必要な検証を実行できない場合は、理由、未検証範囲、再検証手順を記録してください。未検証を合格にせず、必要な検証が完了するまで、その範囲のレビューは保留にします。

既存の自動検査の実行方法は[開発ツール案内](../../tools/README.md)を参照してください。全R項目を自動検出するツールがあるとは扱わないでください。読みやすさ、命名、責務、説明の意味、アルゴリズムと危険操作は、差分と実装を読んで判断してください。

## 仕様書・設計書・操作説明（R17〜R20）

機能や操作を説明する文書には、次の4項目を記載してください。繰り返しになる場合は、読み手が直接参照できる該当節へのリンクを示してください。

1. 背景：なぜ必要になったか、どの状況が問題かを説明してください。
2. 目的：誰が何をできるようになるか、何を改善するかを説明してください。
3. 手段：アプリが何を使い、何をし、どのような制約があるかを説明してください。
4. ユーザーの実行方法：前提、編集・保存するファイル、起動方法、入力・クリックする操作、期待結果、失敗時の対応を記載してください。内部契約だけの文書には、直接操作ではないことと、対応する操作文書または開発者用の実行方法を示してください。

利用者への操作指示は「〜してください」、アプリの動作は「〜します」「〜になります」で書いてください。たとえば「F5キーを押してください。アプリは現在地を保存します。保存すると、次回起動時に保存した位置から始まります。」と書いてください。「保存する」「保存される」だけでは、誰が何をするか分かりません。

仕様書では、前提、入出力、状態の所有者、実行順、変更・保存時点、失敗条件、未対応範囲を明記してください。操作手順と内部設計を混ぜないでください。用語を統一し、略語や専門語には初出で説明を付けてください。

主語と述語を対応させ、曖昧な指示語や長い名詞の連結を避けてください。文書を保存する前に、初めて読む利用者が「何を編集し、何を保存し、何を実行し、何が起きるか」を説明できるか確認してください。

## この規約を使う手順

実装前に本規約と関連する設計・データ契約を読んでください。変更中はR項目へ照らし、検査が必要な箇所を洗い出してください。レビュー時には、存在する場合はローカル専用/レビュー基準.mdも読んでください。このファイルはGit管理から除外するため、新しいcloneにはありません。

提出前に、差分、テスト、文書、性能、安全性の証拠を確認してください。レビュー結果は対象のファイル・宣言、R番号、具体的な問題、修正案、確認方法を対応させて記録してください。根拠のない好みだけで拒否したり、改善のために無関係な変更を混在させたりしないでください。
