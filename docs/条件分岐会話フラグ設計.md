# 条件分岐会話・進行フラグ設計

## 目的

既存の固定モブ会話デッキを壊さず、進行状況に応じた会話選択と会話後のフラグ更新を追加できるデータ契約を定義する。

この文書は契約と責務配置を定める。全イベント機能の実装は後続Issueで行う。

## 後方互換

既存の固定モブは次の形式をそのまま使用できる。

```json
{
  "dialogue": ["こんにちは。", "今日はいい天気ですね。"]
}
```

`dialogue` の意味や `FixedMobController` の会話デッキ動作は変更しない。

条件付き会話を必要とする固定モブだけ、新しい `dialogue_rules` を追加する。

## dialogue_rules

```json
{
  "dialogue_rules": [
    {
      "id": "after_rescue",
      "lines": ["助けてくれてありがとう。", "村のみんなも安心しています。"],
      "conditions": [
        {"flag": "story.greenwood.rescued_child", "equals": true}
      ],
      "effects": [
        {
          "type": "set_flag",
          "flag": "npc.starting_town.elder.thanked_player",
          "value": true
        }
      ],
      "once": true
    },
    {
      "id": "before_rescue",
      "lines": ["森へ行った子どもが戻ってこないんだ。"],
      "conditions": [],
      "effects": [],
      "once": false
    }
  ]
}
```

### 選択規則

- `dialogue_rules` は配列順に評価する。
- `conditions` がすべて成立した最初のルールを選ぶ。条件同士は AND とする。
- `conditions: []` は常に成立するため、通常は最後のフォールバックとして置く。
- 成立するルールがなければ既存 `dialogue` へフォールバックする。
- `lines` は1件以上の文字列。選ばれたルール内では既存会話デッキと同様に一巡するまで重複を避けてよい。
- 不明なルールキーは将来拡張用として無視できるが、不明な condition/effect の `type` は黙って成功扱いにしない。

## conditions

初期契約では真偽フラグ比較だけを扱う。

```json
{"flag": "story.greenwood.rescued_child", "equals": true}
```

- `flag`: フラグID。
- `equals`: `true` または `false`。
- 保存データに存在しないフラグは `false` として読む。
- 文字列比較、数値比較、所持数比較などは本Issueへ含めない。必要になった時点で condition の `type` を追加する。

## effects

初期契約ではフラグ更新だけを扱う。

```json
{
  "type": "set_flag",
  "flag": "story.greenwood.rescued_child",
  "value": true
}
```

- `effects` は上から順に適用する。
- `set_flag` は既存 `state.json.flags` と `FieldProgressStore.set_flag()` を利用する。
- アイテム増減、戦闘開始、マップ移動などは別effectとして将来追加できるが、本契約では定義しない。

## once

`once: true` は、そのルールをセーブ単位で一度だけ選べることを表す。

後続実装ではルール選択時に次の内部フラグを自動記録する。

```text
npc.<map_id>.<npc_id>.dialogue.<rule_id>.seen
```

このフラグが `true` の `once` ルールは条件成立後も再選択しない。明示的な `effects` に seen フラグを記述する必要はない。

`once: false` または省略時は繰り返し選択できる。

## フラグ名前空間

新規フラグは必ずドット区切りの名前空間を使う。

| Prefix | 用途 | 例 |
|---|---|---|
| `story.*` | ゲーム全体の物語進行 | `story.greenwood.rescued_child` |
| `map.*` | 特定マップの状態 | `map.greenwood.bridge_open` |
| `npc.*` | NPC固有の会話・関係・一度きり状態 | `npc.starting_town.elder.thanked_player` |
| `item.*` | アイテムに関するイベント事実 | `item.ancient_key.examined` |

既存の `story_complete` / `ghost_entrance_open` など名前空間なしのフラグは旧セーブ互換のため削除・改名しない。新規コンテンツから名前空間方式を使用し、移行が必要な場合は別Issueで扱う。

## 責務配置

条件評価と永続化を混ぜない。

```text
map/fixed_mob JSON
        |
        v
pure condition/rule evaluator
        |
        v
FieldEventApplication
  -> plain-data dialogue/effects
        |
        v
RuntimeOrchestrator
        |
        v
FieldProgressStore
  -> state.json.flags を保存
```

- 条件評価器: pygame・file I/O非依存。`flags` と `dialogue_rules` を受け取り、選択結果だけ返す。
- `FieldEventApplication`: NPC interactionから選択済み会話とplain-data effectを組み立てる。保存処理を直接行わない。
- `RuntimeOrchestrator`: effectを対応するアプリ/保存処理へ配送する。
- `FieldProgressStore`: 既存 `set_flag()` を使い永続化する。
- `FixedMobController`: 移動と従来会話デッキのruntime stateを担当し、ストーリーフラグの意味を判断しない。

条件評価器の具体的なモジュール名は後続実装時に `core/` の責務と合わせて決める。少なくともpygame、セーブファイルI/O、描画を持たせない。

## エラー方針

- `dialogue_rules` が無い固定モブは完全に従来挙動。
- 空または不正な `lines` はそのルールを無効として扱う。
- 不正なフラグID、bool以外の `equals/value`、未知のcondition/effect typeは開発時バリデータで検出する。
- MOD互換のため未知のトップレベル追加キーは従来どおり許容する。

## 後続実装の最小単位

1. pure condition/rule evaluator
2. `FieldEventApplication` との接続
3. `set_flag` effectの配送
4. `once` seenフラグ
5. project validator / map editor validation
6. 条件付き会話を使う実ゲームデータ

この順序なら既存の単純会話を維持したまま段階導入できる。
