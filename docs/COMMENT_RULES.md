# 宣言コメント

正本は [Json-like-comment-outs 日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md)。導入時に確認した公開版は Draft v0.9 / `5691767a8708407a568a75a242543a4add825253`（2026-10-06）。未公開のローカル仕様や設計段階のupstreamツールを実装済みと扱わない。

今回の明示依頼により、#212の「触れる領域から段階移行」より全コードへの適用を優先した。ゲーム機能は変更しない。次のGDScript P1実装は引き続き#251（基本ぼうぎょ）。

## 対象と書き方

追跡中のPython/GDScriptすべてのクラス・関数・メソッドが対象。非公開、ネスト、property、decorator付き、テスト、ツールも省略しない。Pythonは`#`、GDScriptは`#`、バッチは`rem`を使う。宣言に付随するdecoratorの前へ置く。Windowsバッチは既定のOEM文字コードでも実行できるよう、upstreamの英語キーとASCII説明を使用する（日本語UTF-8コメントの実行時文字コード衝突を回帰検証した）。

クラスには責務と主要フィールド、関数には責務・意味のある処理順・実際の引数名・戻り値を書く。引数なしは`引数: []`、void/Noneは「なし」と明記する。self/clsも入力一覧に含める。必要な箇所だけ副作用/エラー/補足を追加する。

```python
# {
#   責務: [save: 個体と学習済みAIを保存する]
#   処理: [
#     1: 個体JSONを書き込む
#     2: AIのJSONを書き込む
#   ]
#   引数: [
#     self: 保存先を所有するStore
#     record: 保存する個体
#   ]
#   戻り値: [result: なし（None）]
# }
```

複数エントリは実コードと検査で区別しやすいよう別行へ分ける。単一エントリは上記のように1行にまとめてよい。日本語キーを統一し、既存の正しいdocstring/通常コメントは保持する。既存説明が英語の場合は無理に意味を変えず引き継ぐ。

モジュール/名前のないGDScriptクラスにも責務を示すヘッダーを付ける。宣言のないラッパー/空のpackage、バッチの入口/ラベル、実行CIワークフローも対象にする。JSON・画像・シーン/config・依存定義・文書内サンプルは実行ソースの宣言ではないため、コメントのために形式を壊さない。lambda/匿名コールバックや内部の分岐は通常コメントの対象であり、名前付き宣言へ書き換えない。

## 保守と検査

処理、入出力、保持状態を変えたらコメントも更新する。実装をただ言い直すより意図・制約・理由を優先する。テストの検証名は期待動作を表す説明として扱うが、それを実GUI/export/CI成功の証拠と混同しない。

```text
python tools/comment-check/script/check_comments.py
python -m pytest tests/test_comment_contract.py
```

標準検査は`git ls-files`からソースを列挙する。新規ファイルは完了ゲート前に今回分だけstageする。個別調査はパス引数で指定できる。ファイル/実セーブは変更せず、ゲームをimportせず、外部通信も行わない。PythonはASTで全宣言、GDScriptは名前付き宣言と現行の複数行/型付き配列シグネチャを調べ、解析できない名前付き宣言は失敗させる。新しい構文を採用するときは検査と回帰テストも拡張する。

不足項目、空欄、宣言名、引数名、処理番号、既知Semantic Keyの重複を失敗にする。未知キーは推測変換しない。英語別名は大文字小文字を区別しない。自然言語の正確性、全処理の説明品質、主要フィールドの網羅性は静的検査だけでは保証できず、実装とのレビューが必要。

これはKadokaの対象範囲を守る狭いDeveloper/CI検査であり、upstreamの汎用Parser/Validatorをforkしたものではない。導入時点でupstreamは設計段階。利用可能になったら実装を複製せず、その入口へ接続する。Player runtimeから検査をimportしない。

UPD checkerの既存UPD401は物理行数を使うため、コメントだけで警告が増えることがある。今回のAST不変の注釈では警告13→17、エラー0。閾値変更やignoreで隠さず、上流報告は公開承認を得てから行う。これは新しい実装責務を追加した証拠ではない。
