# Issue優先度方針

GitHubの優先度ラベルは `priority: p0` 〜 `priority: p4` を使用する。数字が小さいほど先に扱うが、P0は通常の「最優先」ではなく緊急対応用として空けておく。

| 優先度 | 用途 | 判断例 |
| --- | --- | --- |
| P0 | 緊急対応専用 | 起動不能、保存データの破損/喪失、進行不能など、待たせられない障害の復旧。通常は空。 |
| P1 | 優先して進める | 重要な改善、現在の開発を妨げる依存の解消、早めに必要な機能。緊急障害ではない。 |
| P2 | 普通の対応 | 通常の実装・不具合修正。新規Issueの既定値。 |
| P3 | 後回しでよい | 上位対応の後でも支障の少ない改善・整理。 |
| P4 | 将来・長期保留 | 将来的な構想、前提や着手条件がまだ整っていない機能。着手時に再評価する。 |

## 付け方と見直し

- 1つのIssueに優先度ラベルは1つだけ付ける。種別ラベル（bug/enhancement等）とは別に判断する。
- P0には緊急性の根拠・影響・復旧の受け入れ条件を記載する。単に重要、コンテキスト削減、リファクタリング、将来の移植という理由ではP0にしない。
- 緊急状態が解消したら、残りの改善をP1/P2等へ分ける。P0を通常作業の待ち行列として使わない。
- 未分類の既存Issueは、内容を読んで通常のP2を出発点に評価する。親Issueやタイトルだけで一括昇格/降格しない。
- 既存のhigh/medium/lowはそれぞれP1/P2/P3へ対応させる。criticalは緊急性を再確認し、緊急でなければP1以下へ移す。P4を後回しのP3と区別する。

## 作業の選び方

P0があれば最初に緊急性を確認し、復旧を優先する。通常はP1 → P2 → P3 → P4。同じ優先度なら依存関係を先に解消し、実装可能な最小の子Issueを選ぶ。親Epicの優先度は子Issueの完了や着手可能性を保証しない。

`tools/task-workflow/script/start_task.bat` は、最高優先度にある最古の未完了Issueを候補として1件返す。依存関係・実装済み状態の判断は本文と現行コードで行う。ラベル未設定のIssueはこのツールの選択対象外なので、評価時に優先度を付ける。

ユーザーが具体的な作業を指定した場合はその指示を優先する。ただし未解決の緊急障害が判明した場合は影響を伝える。P4も永続的な却下ではなく、必要になった時点で見直す。
